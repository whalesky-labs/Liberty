## 根因与变更

队列原先已经批量读取任务与来源文件，不存在逐任务追加查询的问题。分配采样显示，逐行新建的 Scan 目标和投影临时结构会逃逸到堆。首批优化仅复用单次查询内的扫描存储和目标地址；每行先重置整个结构，保留返回值独立性，尤其不能让 nullable 字段沿用上一行的指针。

首批没有改变 SQL、排序、读取事务、可见性过滤、JSON 容错、错误码或 LiveReader 状态覆盖逻辑。回归覆盖相邻任务的 nullable 字段、独立文件/JSON 切片、说话人值/NULL/空字符串及 Rust 对非字符串 JSON 的回退语义。未增加数据库索引、连接或依赖。下述第二批另有一次有界容量计数查询，不能把本段首批范围套用到全部当前实现。

## 同设备结果

同一 Rust 合成库含 1000 个任务及来源文件、10000 段逐字稿。修改前后各保留独立测试二进制，交替运行三对基准，每种操作每轮至少一秒；下表为三轮中位数。

| 操作 | 原 B/op | 新 B/op | 分配字节变化 | 原 allocs/op | 新 allocs/op |
| --- | ---: | ---: | ---: | ---: | ---: |
| 队列 | 2,783,363 | 1,887,678 | -32.2% | 43,124 | 36,127 |
| 逐字稿 | 4,666,047 | 4,026,088 | -13.7% | 90,294 | 80,293 |

这是累计分配量，不是常驻或峰值内存。延迟样本受并行任务影响明显，逐字稿中位数还出现回退，当前证据不支持宣称读取更快；应在无竞争负载下继续验证。分配采样支持原行扫描临时对象减少，但切片增长、SQLite 文本转换及结果结构仍有显著成本。

基准为 `BenchmarkReadProjection`，已纳入 `pnpm native:bench:reads`：脚本生成同一合成库，先执行 Rust release / Go 延迟检查，再执行三轮 Go `-benchmem`，最后清理夹具。该命令只比较当前实现，历史前后对照需要保存对应版本的二进制及相同输入，不能拿不同机器或不同数据库混比。

## 本批完整命令复验

主代理随后完整执行 `pnpm native:bench:reads`，Rust release 生成夹具、两端延迟校验及三轮 Go 分配基准均通过。每项预热两次，测量 20 次，延迟单位为毫秒：

| 操作 | Rust P50 / P95 | Go P50 / P95 |
| --- | ---: | ---: |
| 队列 | 2.610 / 2.867 | 4.614 / 5.825 |
| 逐字稿 | 3.708 / 3.872 | 7.777 / 8.328 |

本次 Go 仍较慢，不能以检查退出 0 认定性能目标已达成。三轮 Go `-benchmem` 的队列分配约 1,887,515–1,887,614 B/op、36,127 allocs/op，逐字稿约 4,025,818–4,025,925 B/op、80,292 allocs/op，与此前局部分配结论一致。两端测量仍不包含窗口绘制、冷启动或 ASR；该次短样本也不替代完整资源预算验收。

## 第二批：JSON、数值扫描及逐字稿初始容量

在首批版本上继续检查分配来源后，字符串数组改为一次解码，保留根 `null`、数组内 `null` 和非字符串元素的原严格回退行为。空数组快速返回非 nil 空切片；导出格式的默认切片只在确需回退时创建，合法空数组不改成默认值。数值 scanner 对常见 SQLite 非负整数直接做范围检查，其他输入保留原 `database/sql` 转换规则。真实 SQLite 对照覆盖空值、符号、浮点、溢出和字节输入。

逐字稿在原有只读事务内先按任务及类型执行 `COUNT(*)`，再预分配结果切片。初始容量最多 65,536，超过仍继续追加，没有返回条数限制；65,537 段逆序夹具验证全量与投影顺序。这个额外查询可能增加短记录的开销，不能仅凭长逐字稿的分配下降断言所有读取更快。schema、索引、事务边界和持久化数据没有变化。

相同合成库、同一设备上保存首批和第二批各自的测试二进制，固定每种操作 200 次，交替先后次序运行四对；下表为四轮中位数，基线已经包含首批改善，不能与前表百分比混算。

| 操作 | 首批 B/op | 第二批 B/op | 分配字节变化 | 首批 allocs/op | 第二批 allocs/op |
| --- | ---: | ---: | ---: | ---: | ---: |
| 队列 | 1,887,886 | 1,727,001 | -8.5% | 36,127 | 29,125 |
| 逐字稿 | 4,026,093 | 1,777,484 | -55.9% | 80,293 | 60,310 |

四对测试进程 user + sys CPU 时间分别为首批 3.81 / 2.59 / 2.53 / 3.13 秒，第二批 2.76 / 2.45 / 2.20 / 2.37 秒。局部延迟中位数为队列 4.805 → 4.097 ms、逐字稿 9.646 → 7.405 ms；样本仍受其他负载影响，这些数字只支持本夹具的局部改善，不是整应用性能验收，也不是相对 Rust 的最终对比。

第二批 `legacydb` race 回归通过（10.539 秒）；严格 JSON oracle 的 10 秒 fuzz 通过 97,013 次执行。原始四对输出及 CPU 时间保存在忽略的 `target/native/`，输入由 Rust benchmark 生成，不使用用户资料库。

## 尚未覆盖

尚未据此验收冷启动、完整 UI 长列表、多结果窗口、动画、整进程内存、并发 ASR 或其他平台。性能退出条件仍以已确认重构方案为准：完整场景的 CPU、内存、延迟和稳定性都需测量，不能把局部分配下降作为生产切换依据。方案没有把 Go 只读查询必须快于 Rust 规定为单独放行阈值；前述差异用于识别成本，不能据此擅自添加或放宽验收条件。

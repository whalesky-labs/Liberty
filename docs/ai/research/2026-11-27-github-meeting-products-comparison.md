## 1. 判断

Liberty 所处的市场已经存在多款“本地转写 + 说话人分离 + AI 总结”产品。仅靠这些功能，或仅强调“中文、本地、Word 导出”，不足以形成明显差异。

更值得验证的定位是：**免费、普通电脑易用的中文本地会议工作台，基础流程无需付费 API，将人员、转写、核对和结果导出连接起来，并提供离线中英实时翻译；用户可按需调用 AI 整理正式纪要。** 人员、正式纪要与本地中英翻译已有实现，完整核对编辑链路仍有缺口；低配置体验和用户迁移意愿仍需验证。

### 已确认的产品约束

- **产品免费。** 不向 Liberty 的基础会议能力引入订阅、按次收费或付费墙。
- **基础流程无付费 API 成本。** 录音/导入、转写、说话人处理、查看、校对、非 AI 结果导出和本地翻译，不以付费接口或 API Key 为前提。
- **AI 整理纪要是唯一已确认的 API 费用例外。** 用户主动选择时，其模型服务可以产生费用；这不表示 Liberty 自身收费或强制使用收费服务，不配置 AI 也应能完成基础流程。不得将例外扩展到会议问答或其他云端功能。
- **降低安装与配置门槛。** 环境和模型由应用管理，普通用户不应为核心功能手工部署 Python、CUDA、Docker、WSL 或 Ollama；首次联网下载与付费 API 成本分别评估。
- **普通配置优先。** 不将独显、高显存、大内存和本地 LLM 设为基本使用前提。按需加载、退出释放、低并发和受控后台占用应优先于扩大模型与功能数量；最低配置仍须实测，不在本轮指定或承诺。

这些目标已同步至[项目规则](../../../AGENTS.md)，并非当前版本已达到全部目标的验收结论。后续竞品评价先比较实际费用、首次成功所需步骤和普通电脑资源占用，再比较功能覆盖。支持本地大模型、团队服务或更多 AI 功能本身不自动构成更适合 Liberty 的方向。

### 按产品目标重新评估

2026-11-27 按上述目标复核了七款主要产品的官方仓库及相关安装、模型文档。以下是对标价值判断，不是性能或质量排名；竞品依然未安装实测。

| 产品 | 免费与 API 边界 | 安装及配置门槛 | 普通电脑方面的证据与限制 | 对 Liberty 的对标价值 |
| --- | --- | --- | --- | --- |
| Vibe | 开源本地转写无需付费转写 API；总结可选 | 有桌面下载入口；不必为基础转写部署本地 LLM | 有模型选择、GPU 加速与运行时模型加载/卸载设计；尚无本轮统一低配置实测 | 第一组实测对象：免费桌面工具本身已有较广输入输出能力，不能只靠“免费+导出”区分 |
| Buzz | 开源本地转写无需付费转写 API；远程 API 与总结插件可选 | 有安装包；系统声音需按官方说明配置虚拟音频设备 | 官方建议较小模型或 Whisper.cpp；该后端支持 CPU-only；旧 CPU 的 AVX2 与 Intel Mac 版本有边界 | 第一组实测对象：优先学习普通设备模型选择、回放查看器与快捷操作 |
| Tingji | 本地 ASR 不收费，纪要可选本地或 API；免费边界与目标接近 | Python/uv、ffmpeg、本地服务，Windows 使用 WSL2，普通用户配置步骤较多 | 官方实时标准模式列出现代 CPU、8GB+ 内存；GPU 实时增强当前禁用；该自报要求不是本轮验证 | 中文功能重点对标：人工校对、说话人修正、纪要编辑和来源回跳；不照搬其部署路径 |
| Meetily 社区版 | 本地转写免费；README 将说话人识别、模板及 DOCX 等列为 Pro，超出 Liberty 仅 AI 纪要可有 API 费的产品边界 | Windows/macOS 有安装包，基础转写不需要另部署 FastAPI/Docker 后端 | Windows 包要求 AVX2；支持多种加速，低配置实时效果未实测 | 学习采集与设备交互；保留 Liberty 将会议基础能力免费提供的方向 |
| noScribe | 免费本地转写、说话人与人工校对，不依赖收费转写 API | 有标准安装包与编辑器；官网称含模型安装包约 3 GB | 有无 NVIDIA GPU 的标准版；新版本不再提供 Intel Mac 官方包；本轮没有速度实测 | 访谈与校对专项对标；证明“免费+本地+说话人”也不是独有组合 |
| anarlog | 社区应用开源，可选择本地、付费托管或自带服务；不能把所有可选云服务都算成必需支出 | 有桌面下载；选择本地能力时需核对 Mac、系统、模型与语种条件 | 内置本地转写路径受支持 Mac 限制，Parakeet 路线与 Apple Speech 的语言/系统范围不同 | 学习笔记和会议体验；不能把云端方便程度当成本地免费路径同样易用的证据 |
| Scriberr | 可自托管免费 ASR，支持 CPU 部署；本地 LLM/云端总结与问答另计 | Homebrew 或 Docker 服务，需管理环境、模型及数据目录 | 有 CPU 和 NVIDIA 镜像选择，不代表必须独显；整体普通配置体验未实测 | 参考播放定位、笔记与自动化，不把服务部署、本地 LLM 和问答带入默认门槛 |

以上依据 [S1]–[S7]、[S9]–[S11]。费用判断只覆盖所述本地路径；开源或离线不代表没有首次下载、硬件、电力和操作成本。

因此，后续对标顺序调整为：**Vibe/Buzz 验证免费桌面使用体验；Tingji 验证中文会议交付；Meetily 验证系统声音采集；noScribe 验证人工校对。** anarlog 与 Scriberr 用于选择性参考。免费桌面体验、中文功能、采集和校对是不同实验方向，不将其强行排成一个未经实测的综合分数榜。

Liberty 更有价值的目标是“免费基础流程 + 无需 Key + 易安装 + 普通电脑可用 + 中文正式材料”，目前证据还不足以宣布这套组合已经领先。只要 AI 纪要由用户主动选择，调用所选服务产生费用就符合目标；无需为了消除这项可接受费用而强制部署更大的本地 LLM。会议问答、云端同步或复杂集成不因竞品支持就自动升级为我们的优先任务。

重点对标对象分为三组：

- **完整会议助手**：Meetily、anarlog、Tingji、licycle 的 macOS FunASR 会议工具。
- **桌面转写与字幕工具**：Vibe、Buzz、noScribe，适合对标批处理、校对、播放器和字幕体验。
- **自托管工作台**：Scriberr，适合对标音频问答、自动化与服务化部署。

Liberty 的近期优先级应放在免费基础流程、普通配置资源预算、首次安装、录音入口、校对与证据回溯以及平台验收。桌宠是产品个性和留存假设，尚无证据证明其能弥补会议主流程的不足，其后台资源占用也应纳入普通配置预算。

## 2. 比较方法与限制

1. 优先查看项目自己的仓库与文档，而非第三方榜单。竞品功能均视为官方声明，本轮未下载安装、录制会议或复现其宣传性能。
2. 区分社区版、商业版和路线图。没有找到能力声明时记为“未核实”或“非主打”，不据此断言不存在。
3. 区分本地 ASR、本地数据存储与本地 LLM。前两者成立，不代表云端总结不会发送会议文本。
4. 区分说话人分离、人工改名和真实身份识别；分成 Speaker A/B 不等于自动知道参会者姓名。
5. 区分源码、发布资产和实机验收。Liberty 以当前 `apps/native` 候选为基线，不将仍保留的旧生产入口当成新版完成证明。
6. 不以 GitHub Star 数推导用户规模、准确率或可靠性。本轮读取了部分仓库实时元数据；后续 API 触发未认证访问限流，因此不制作不完整的热度排名。
7. 未执行同机、同录音、同模型条件下的 CER/WER、DER、延迟、内存、功耗或纪要事实准确性对比，不能给出质量冠军或性能排名。

## 3. Liberty 的当前基线

| 维度 | 当前证据与边界 |
| --- | --- |
| 文件任务 | 单次创建一个本地音视频文件任务；有队列、搜索筛选、详情、重试与删除；不能当作已有多文件批量导入入口。 |
| 识别与说话人 | FunASR 本地流程；已验证说话人标签可筛选和改名；分离失败时保留原逐字稿。没有本轮统一识别质量排名。 |
| AI 总结 | 用户主动发起，兼容 OpenAI 风格接口，有模板、持久化输入/分块/重试和历史结果。本机回环 IP 服务允许接入，但不等于应用内置了开箱即用的本地总结模型。 |
| 正式纪要 | 人员 Excel、部门、记录人等管理；会议名称、时间、地点、出缺席、主持人与审阅等元信息投影；TXT、Markdown 与 DOCX。 |
| 校对 | 文件结果页有文本搜索、说话人筛选与改名；正文以可选择文字展示，当前所查结果页没有音频播放器或逐句正文编辑入口；纪要窗口只读。实时字幕历史另有原文/译文编辑，不能混同于文件逐字稿编辑。 |
| 实时翻译 | 麦克风中英转写，按定稿文字自动选择中英翻译方向，本地 Argos/CTranslate2，不需要翻译 API Key；可补译、编辑与导出双语 SRT/VTT/TXT。 |
| 实时边界 | 尚无系统声音、其他语种、悬浮字幕或译文朗读；实时音频不落盘，只保存定稿与状态；与文件 ASR 互斥。 |
| 数据与安全工程 | SQLite 持久化任务、attempt/lease、事件、总结快照；系统凭据库保存密钥，导出与迁移有相应边界。这是源码设计证据，不等于相对竞品安全性已经验证领先。 |
| 平台与交付 | 目标为 macOS ARM/Intel 与 Windows x64；原生候选尚未完成全部 UI、平台、生产切换等验收；更新是打开 Releases 后由用户下载安装。 |
| 首次使用 | 托管 Python、ffmpeg、依赖与模型需要安装；实时模型约 990 MiB，其他环境与默认模型另计。离线运行不等于首次安装离线。 |
| 陪伴 | 桌宠、成长、签到、商店、农场与打工等本地玩法已存在；不阻塞主会议流程，无真钱语义；留存收益未核实。 |

## 4. 主要竞品

### 4.1 Meetily：直接对标会议采集与会议助手

- 仓库：`Zackriya-Solutions/meetily`，社区应用 MIT。[S1]
- 官方声明：Whisper/Parakeet 本地转写、麦克风与系统声音同时采集、实时文字、音频导入、本地 Ollama 或云端/兼容接口总结，提供 Windows 与 macOS Apple Silicon 安装入口。[S1]
- **优势**：会议采集入口比 Liberty 当前仅麦克风的实时入口完整；本地 LLM 有明确推荐路径；有 GPU 与打包平台说明。[S1]
- **边界**：README 将说话人识别、自定义总结模板、PDF/DOCX 等高级导出和 MCP/CLI/webhook 集成列为 Pro 能力；会议问答与日历集成仍标为 Coming Soon。不要把仓库简介、Pro 宣传与免费社区版合成一套已交付功能。[S1]
- **对 Liberty 的含义**：需要优先学习系统音频与麦克风的采集、混音和设备交互。Liberty 的免费说话人流程、自定义总结模板和正式纪要组合有比较空间，但不能宣称 Meetily 整个产品没有这些能力。

### 4.2 anarlog：直接对标会议笔记、编辑与 AI 工作流

- 仓库：`fastrepl/anarlog`。社区应用 MIT，`enterprise/` 等企业部分使用商业许可证。[S2]
- 名称核对：它原为 Hyprnote，曾短暂使用 char 名称；当前 anarlog 仓库与团队现在的 char 产品已分开，不能拿旧 Hyprnote 印象代替当前实现。[S2]
- 官方声明：设备侧采集、SQLite 与本地文件、可编辑会议笔记、Markdown 导出、总结与对话、可选本地或自带模型服务、默认关闭的可选加密同步；下载入口覆盖 macOS/Windows/Linux。[S2]
- **优势**：将实时会议、用户手记、AI 整理与编辑组织为一条工作流；本地数据与可选同步的边界清楚，仓库还有 CLI/MCP 与移动端 beta 等扩展入口。[S2]
- **边界**：README 对内置本地转写明确限定为受支持 Mac 上可用，其他平台与具体 provider 的离线能力需逐项检查；托管 Pro AI 会走所选云服务。不能把“有 Windows/Linux 下载”理解为每个平台具备相同离线能力。[S2]
- **对 Liberty 的含义**：应对标“边开会、边做笔记、会后继续编辑”的连续体验，而非追求菜单数量。Liberty 的人员/部门与固定纪要模板可保持垂直差异。

### 4.3 Tingji：最值得关注的中文工作流竞品

- 仓库：`baigong-ai/Tingji`，MIT。[S3]
- 官方声明：FunASR、CAM++、本地 Ollama/兼容 API；批量上传；原文校对；说话人合并与逐句重新分配；倍速与跳静音；结构化纪要；纪要和议题时间戳回跳；独立个人批注；整理稿/总结二次编辑；DOCX/Markdown/TXT/SRT；实时录音后后台二次识别。[S3]
- **优势**：围绕中文会议的“核对—整理—纪要”链路，比只生成摘要更完整。其音频回跳、人工纠错、笔记不被重新生成覆盖，直接对应 Liberty 目前的体验缺口。[S3]
- **边界**：部署方式以 Python、ffmpeg、本地服务与浏览器为主，Windows 说明采用 WSL2；README 明示无用户认证，仅适合本地或可信局域网，任务状态有内存边界。其补充恢复机制不能等同于完整持久化调度；增强 GPU 实时模式当前禁用，不能计为可用能力。[S3]
- **对 Liberty 的含义**：“中文 + FunASR + DOCX”已经被覆盖。更可信的竞争方向是安装便利、原生交互、人员与正式材料模板、可恢复任务，以及中英离线实时翻译的组合；这些收益仍需实测证明。

### 4.4 Vibe：对标多格式、批处理与桌面交付

- 仓库：`thewh1teagle/vibe`，MIT。[S4]
- 官方声明：Windows/macOS/Linux，本地多语种转写，Whisper/Nemotron/Parakeet，批处理、网页媒体、系统声音和麦克风、说话人分离，SRT/VTT/TXT/HTML/PDF/JSON/DOCX，多种 GPU，Ollama/Claude 总结，自动更新与 CLI/HTTP API。[S4]
- **优势**：输入、输出、模型和自动化覆盖面广；对普通转写和字幕用户，使用路径可能比会议专用工作台直接。后者为产品适配判断，本轮未计时测试。[S4]
- **边界**：官方功能列表的重心是通用媒体转写和字幕；人员 Excel、部门及特定正式会议元信息流程未核实。其“翻译成英语”不等于离线中英双向实时翻译。[S4]
- **对 Liberty 的含义**：不能宣称 Word 导出或本地总结是独家优势；优先参考多文件入口、模型设置、字幕格式和更新体验。

### 4.5 Buzz：对标转写查看器与自动化

- 仓库：`chidiwilliams/buzz`，MIT。[S5]
- 官方声明：本地 Whisper 多后端，文件/YouTube、麦克风实时转写、说话人处理、搜索/回放/倍速、监听文件夹、CLI、插件系统，插件可生成 AI 总结；TXT/SRT/VTT 导出。[S5]
- **优势**：播放器、快捷键、文件夹自动转写等能显著影响日常效率，值得 Liberty 学习。其优势在功能路径，不代表本轮已验证准确率或速度领先。[S5]
- **边界**：总结属于插件能力，完整人员/正式纪要流程未核实；当前 README 明确新版本 macOS 要求 Apple Silicon，Intel 最后支持版本为 1.4.5，不能笼统写成当前全 Mac 架构支持。[S5]
- **对 Liberty 的含义**：在专业纪要之外，应先保证转写结果易查、易听、易改。其 FAQ 明确推荐较小模型或可仅用 CPU 的 Whisper.cpp 路径，并要求系统声音通过虚拟音频设备接入；这些分别是低配置选型和音频配置门槛的参考。Intel 支持可以成为目标差异，但 Liberty 尚未完成的实机验证不能当成现成优势。[S9]

### 4.6 noScribe：对标访谈与人工核验

- 仓库：`kaixxx/noScribe`，GPL-3.0-or-later。[S6]
- 官方声明：面向质性研究与新闻访谈，本地 Whisper/faster-whisper/pyannote，多说话人与多语言，配有审核和修正逐字稿的编辑器，覆盖 Windows/macOS/Linux。[S6]
- **优势**：目标用户明确，把“可信且能人工修正的逐字稿”作为中心。若 Liberty 面向科研或访谈用户，这是比小游戏数量更贴近需求的对标。
- **边界**：本轮所查入口没有确认完整 AI 会议助手、组织人员或业务纪要流程，不把这些标为绝对不存在。官网提供无 NVIDIA GPU 的标准版，但含模型安装包约 3 GB；当前 Apple Silicon 版要求 macOS 14+，Intel Mac 最后的官方版本为 0.6，不能将“三平台”理解为当前覆盖所有 Mac 架构。GPL 许可与 Liberty 的 MIT 不同，借鉴交互不等于可以直接复制代码。[S6][S10]

### 4.7 Scriberr：对标自托管、问答与自动化

- 仓库：`rishikanthc/Scriberr`，MIT。[S7]
- 官方声明：本地音视频转写、多模型、说话人分离，播放跟随与文字定位，笔记/高亮，本地或兼容接口总结和音频问答，API、文件夹监听，Homebrew/Docker 服务与 PWA。[S7]
- **优势**：比桌面单机窗口更接近可接入自动化的自托管工作台；“问会议内容”和边听边记是 Liberty 可参考的会后消费能力。[S7]
- **边界**：要管理服务、环境、模型、存储卷及可选 GPU，普通桌面用户的配置成本更高是合理推断，未做定量测试。README 有维护暂停后准备恢复的说明，不据此推断其已停更或存在团队服务承诺。[S7]
- **对 Liberty 的含义**：可研究后续问答与导入自动化，但目前不宜为了对标而引入一套团队服务器或多租户系统。

### 4.8 licycle 的 macOS FunASR 会议工具：相近技术组合的新项目

- 仓库：`licycle/H-VibeRec`，AGPL-3.0-or-later。[S8]
- 官方声明：macOS 本地录音与导入，FunASR/Paraformer/SenseVoice 与可选 Qwen3-ASR，说话人、长文本总结、本地笔记与 AI 问答、全局语音输入，SQLite 与系统钥匙串。[S8]
- **优势**：与 Liberty 的“中文、本地、FunASR、桌面”重合较多，并将语音输入和笔记问答延伸到日常工作。[S8]
- **边界**：当前明确支持 macOS，其他平台未核实；LLM 功能会向配置的服务发送相应文本；安装包与长时间真实使用成熟度未实测。不能把下载入口存在当作成熟度已经验证。[S8]
- **对 Liberty 的含义**：说明技术栈组合本身容易出现同类方案；真正的区分应来自工作流、质量证据和交付。AGPL 许可意味着不能按 MIT 项目方式随意移植实现。[S8]

## 6. Liberty 的优势与劣势

### 有依据的比较优势与可验证机会

1. **正式材料工作流的组合。** 人员 Excel、部门、记录人、会议信息、结构化内容和模板 DOCX 已有实现。相对通用字幕工具更贴近固定会议材料；相对 Tingji，需要靠模板深度、人员复用和交付体验证明额外价值，不能只强调文件扩展名。
2. **独立的中英本地实时翻译。** 不借用总结 API Key，能编辑、补译与双语导出，是本轮样本中值得重点验证的组合差异；不宣称全市场独有，也不宣称其质量达到商业同传水平。
3. **可靠任务与数据处理的工程基础。** 持久化 job/event、总结快照、系统凭据和迁移/恢复边界已进入代码；相对 README 明示内存任务状态的工具，设计上更注重中断处理，但需以故障实测证明效果。
4. **个人桌面陪伴。** 与所查会议工具的主定位不同，可作为自愿使用的附加价值。收益依据应是实际留存、使用反馈和资源占用数据，当前仍是假设。

### 当前更明显的短板

1. **会议声音入口不完整。** 实时流程仅麦克风，不能可靠涵盖耳机中的远端参会者声音；对在线视频会议而言，这是高影响缺口。
2. **从 AI 输出到可信材料的人工环节不足。** 文件逐字稿没有在当前结果页形成“回听—改字—调整说话人—保存—更新纪要”流程，纪要窗口又只读；Tingji、noScribe、Buzz/Scriberr 的相应能力值得参考。
3. **批量与自动化入口偏少。** 当前单文件创建，对大量录音整理者不如多文件导入、监听文件夹等方便。这是入口差异，不等于 Liberty 没有后台队列。
4. **知识再利用不足。** 当前查看页是关键词/说话人筛选；在所查源码中未发现可对比 Anarlog/Scriberr 的会议内容对话入口。跨会议语义检索更不能由现有队列搜索推导出来。
5. **首次安装和运行时成本需要降低。** Go 原生 UI 不代表整体程序轻量，Python、Torch、ffmpeg、ASR/翻译模型的下载、加载和运行成本仍然存在；任何“更省内存”结论都需测整个进程树。
6. **交付与成熟度仍有欠账。** 候选身份、手工更新、跨平台和可访问性验收等未全部闭合。安装器脚本存在不等于用户安装、升级、回退已经可靠。
7. **产品焦点风险。** 桌宠/农场/打工可能吸引个人用户，也可能增加会议用户的学习与维护成本。没有用户证据前，不应让附加玩法优先于录音、校对与恢复。

## 7. 建议优先级

以下建议受上述已确认产品目标约束，未修改代码、未批准排期。付费 API 只允许作为用户主动整理纪要的可选费用；本地 LLM、会议问答、团队服务和复杂自动化不进入基础使用前提。

| 优先级 | 建议 | 对应问题 | 应看到的验收结果 |
| --- | --- | --- | --- |
| P0 | 验证无 Key 的免费基础流程与普通配置预算 | 免费、本地不等于低门槛或低资源 | 无 API Key 可完成基础任务与非 AI 导出；CPU 路径可用；按需加载并统计整个进程树；最低配置按实测确定 |
| P0 | 收敛原生候选验收、首次安装与恢复体验 | 能力存在但用户未必顺利使用 | 三目标分别完成首次安装、权限拒绝/恢复、真实任务、重开与恢复；没有用编译代替实机证据 |
| P0 | 设计并验证系统声音+麦克风采集 | 远程会议另一端的声音缺失 | 耳机与扬声器、设备切换、权限拒绝、重复混音、长会议与退出均有结果；录音行为有明确提示 |
| P1 | 建立音频和文字联动校对 | 识别与总结错误难核实 | 点句回听、倍速、逐句修改、说话人改归属、撤销/保存；修改后旧 AI 结论被清楚标记 |
| P1 | 纪要二次编辑、来源锚点与正式模板 | 有摘要但交付前仍需大量人工整理 | 决议/待办能回到来源；人工编辑不被重新总结覆盖；人员和模板可复用 |
| P1 | 多文件导入与清楚的批次状态 | 多录音导入繁琐 | 单独失败不阻塞整批；重试不重复创建；遵守内存与线程预算 |

| P2 | 在费用、资源和配置约束内评估可选会议问答与搜索 | 会后资料再利用 | 不新增付费 API 前提，不强制部署本地 LLM；不能满足普通配置预算时暂缓；答案有来源且不知道时不编造 |
| P2 | 日历、文件夹监听、CLI/MCP 按需求进入 | 自动化不足 | 用真实用户频次证明价值，避免一次扩展过多入口 |
| 持续 | 桌宠保持可选择与资源隔离 | 产品个性与主流程竞争资源 | 关闭后核心能力完整；不抢麦、不阻塞任务；对功耗与留存都有数据 |

## 8. 下一轮实测方案

建议先测 Vibe、Buzz 与 Tingji，分别验证免费桌面体验、普通设备模型路线和中文会议流程；Meetily 社区版补充采集对比，noScribe 补充校对对比。商业 Pro 需与社区版分开记录，不能用免费版本的价格对比商业版的能力。可选 AI 纪要 API 费用符合 Liberty 的产品边界，不将其本身判为缺陷；需比较的是调用是否自愿、费用是否清楚，以及不配置时基础流程是否完整。

使用公开授权或合成材料，固定版本、模型、设备、网络条件和输出要求：

- 中文会议、专业术语与人名、中英混说、多人交叉、远场噪声、纯英语各一类；长会议另设场景。
- 文件转写与实时分别测；端到端默认体验与同模型/相近配置实验分开，避免混淆产品与模型差异。
- 本地 ASR 测 CER/WER、DER、时间戳误差、处理时长；最终材料测决议/待办事实一致性、遗漏和无依据补充。
- 实时测首字、定稿与译文的 P50/P95 延迟、掉字/积压与两小时连续稳定性；使用真实计时，不能把 600 ms 音频块写成 600 ms 翻译时延。
- 资源测整个进程树峰值与稳态内存、CPU/GPU、磁盘和模型下载量；至少分别覆盖 8 GiB 档位与较高配置。
- 费用与门槛单列：记录不配置 API Key 可完成的基础流程、是否要求收费接口、安装与模型准备的手动步骤、首次下载量；不要求用户运行本地 LLM。8 GiB 是现有验收档位，不是本轮确认的最低配置承诺。
- 体验测首次成功耗时、人工校对时间、最终 DOCX 整理时间、无网络行为，以及中断/磁盘不足后的数据恢复。AI 整理纪要的可选调用费用单列，不混入免费基础流程。

本轮没有执行上述实验，也没有改动业务代码、构建、启动客户端或发布。

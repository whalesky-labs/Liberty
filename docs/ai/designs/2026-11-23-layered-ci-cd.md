## 目标与现状

按“改动影响范围 + 风险 + 所处阶段”选择检查。普通提交提供快速反馈，高风险变更补齐专项验证，需要额外回归时手动执行，正式发布验证完整交付物。

资源约束：按 2026-11-23 确认的要求，CI/CD 不配置定时触发。检查由提交、PR、手动操作或发布事件触发；没有这些事件时不启动 GitHub Actions。安全扫描在依赖、锁文件、供应链策略或相关运行时输入变化时执行，也可手动触发，正式发布前必须重新执行。

实施前基线 `23022fe6` 的 `quality.yml` 对每个面向 main 的 PR 和每次 main 推送都运行临时生产端检查，并调用 `build-native.yml`。后者再次执行原生整体检查、Python、完整兼容回放、全包 race、三目标编译、许可证/SBOM、安全扫描以及三个系统上的候选测试和打包。共享 Python 检查重复，两条供应链链路也会扫描重叠输入。Native 工作流配置 `cancel-in-progress: false`，连续提交不会取消正在运行的旧检查。

2026-11-23 实施前查询时，main 的 `protected` 为 false，分支 rules API 返回空数组。设置保护规则属于方案落地的一部分，实施结果须在下方记录，不能仅由源码推断。

支持平台保持三个。旧 React/Tauri 尚处于临时生产阶段，其检查按旧端或共享输入的变化触发；全量与正式发布仍覆盖它。在正式生产切换时删除旧端检查和发布链，不能形成长期双轨。

## 事件与检查层次

| 事件 | 默认执行 | 升级条件与产物 |
| --- | --- | --- |
| 本地编辑、保存 | 不触发远端 CI | 编辑器诊断和开发者按需运行相邻检查 |
| 本地提交 | 可选快速格式、配置检查 | 不把整仓构建、模型下载放进强制提交钩子 |
| PR 创建、更新、转为可评审 | 改动分类、必要静态检查、受影响模块测试、固定结果汇总 | 命中高风险路径则执行对应专项或全量；默认不打三平台包 |
| 推送 main | 对实际提交执行同样的范围判定和必要集成检查 | 高风险变更仍升级；不因来自已测试 PR 就无条件复用其他 SHA 的结果 |
| 手动全量验证 | 指定确切提交，执行完整自动化门禁 | 排障或集中验收时主动运行；可单独选择安全扫描 |
| 手动候选构建 | 指定 main 上的确切提交和目标，校验候选前置条件并打包 | 输出不可生产发布的候选，供人工或设备验收 |
| 发行标签或显式发布操作 | 完整质量门禁、三平台执行、当前安全/许可证/SBOM、签名与安装包校验 | 验证同一提交的最终资产后发布；生产凭据只在发布阶段可用 |

不同时为普通工作分支 push 和该分支 PR 跑同一套检查。建议 CI 监听 `pull_request` 和 `push: main`；需要无 PR 的分支验证时使用手动入口。发布始终绑定不可变版本、确切提交和 Release ID。

## 按改动范围选择检查

以下是工作量选择规则。多类改动取并集；不能让某个文档路径覆盖同一提交中的代码路径。

| 改动类型 | 必须执行 | 通常不触发 |
| --- | --- | --- |
| 纯说明文档：根 README、普通 docs Markdown、模块 README | 链接、Markdown 围栏；命令引用由修改者核对 | Go/Rust/Python 测试、三平台构建、打包 |
| CHANGELOG、版本来源 | 文档检查、版本一致性 | 仅变更说明文字时不触发全量；实际版本变化进入发行预检 |
| TS/TSX/CSS、旧端 UI | 类型检查、前端测试；CSS、资源或入口变化加 Web 构建 | 未影响 Rust/共享契约时不执行 Rust、原生兼容回放 |
| Native Go 普通改动 | gofmt、vet、Go 模块普通测试、Native 必需安全回归；相关生成物核验 | 默认不运行完整跨语言回放、全包 race 和三平台打包 |
| 异步控制器、任务调度、Runner、窗口生命周期 | 上述 Go 检查，加完整 Go 模块 race | 不涉及持久化协议时不自动重放全部经济与数据库夹具 |
| Python Runner、validate/warmup | Python lint/tests、协议夹具、原生资源生成核验及 Go/Rust Runner 适配测试 | 未改变依赖或固定模型时不进行完整模型下载与性能验收 |
| 共享消息、图标、宠物和地图素材 | 相关生成器、引用完整性、数据规则测试、受影响 UI 测试 | 单纯素材变化不触发数据库全量兼容回放 |
| schema/迁移、持久化、资料导入/恢复、凭据所有权、经济规则 | 完整相关兼容回放、持久化重开、失败重试、相关 race；跨系统文件/凭据路径加平台执行 | 不允许把这些变更降为普通界面检查 |
| 共享 Runner/IPC/数据契约 | 所有消费者的生成漂移、协议和适配测试；持久化字段变化追加完整兼容 | 不能只测修改文件所属语言 |
| 平台文件、build tags、Go 工具链或模块依赖 | 三目标编译、受影响平台实际测试；系统凭据相关变更加独立凭据验收 | 普通纯逻辑改动无需每次占用三种系统 runner |
| Rust 平台实现、Cargo 配置或依赖 | fmt、相关 package tests、Clippy；Windows 相关代码加 x64 编译/测试 | 不相关 Native UI 改动不牵动 Rust 编译 |
| 依赖声明/锁、供应链例外、运行时 manifest/vendor/模型清单 | 受影响依赖图的真实安全扫描、许可证/SBOM、锁完整性与安装验证；改变模型/运行时需对应真实运行验收 | 不使用旧扫描结果关闭新的依赖风险 |
| CI、改动分类器、工具链、打包/发布脚本、安装器、全局配置 | 全量质量、分类器/发布策略自测、三目标构建；安装器变更加目标系统验证 | 不通过跳过失败检查让工作流“变绿” |
| 未识别路径或无法可靠取得 diff | 全量检查 | 不默认当作文档或无影响变更 |

第一阶段采用模块级选择：Go 普通变更运行完整 Go 模块普通测试，选中 race 时运行完整 Go 模块，Rust 运行 workspace。暂不引入难以审计的“只跑修改文件对应测试”。实测存在瓶颈后，才增加依赖图和反向调用方分析；分析不完整时扩大检查。

文档快速通道采用明确允许列表。`AGENTS.md`、工作流、配置、schema、生成器输入、`.docx` 模板、可执行示例和锁文件不因扩展名或所在目录而被当成普通文档。生成器源与生成产物都应映射到相同检查范围。

## 工作流划分

建议使用以下入口，底层检查用 reusable workflow 或独立脚本复用：

| 入口 | 职责 |
| --- | --- |
| `quality.yml` | PR/main 的轻量编排：计算计划 → 选择检查 → `ci-gate` 汇总；不再无条件调用候选交付 |
| 新 `ci-full.yml` | 完整自动化验证，只接受调用或手动触发；包含全量单测、兼容、race、平台、供应链和发布策略 |
| `build-native.yml` | 候选构建与资产核验；指定 SHA/目标，验证必需前置结果；不作为普通提交的默认检查 |
| `build-desktop.yml` | 临时生产发布入口，强制调用完整门禁，保持版本、Release ID、资产摘要和权限限制；生产切换时替换并删除旧端发布链 |

将组合命令拆为可复用的检查单元，例如 `native:lint`、`native:test`、`native:generated:check`、`native:policy:check`、Python、前端、Rust、兼容、race、平台执行和打包。现有 `pnpm check` 继续作为开发者主动运行的完整本地入口，保留检查覆盖但消除重复 Python 等步骤。CI 不把这个大入口用于所有改动。

完整验证的质量汇总必须同时依赖测试和安全结果。普通候选产物可以作为诊断留存，但扫描失败时绝不能取得发布资格。新结构要同步重写 `check-native-release-policy.mjs` 的封闭工作流契约和 `check-release-policy.mjs` 的调用/权限校验，并保留、更新所有绕过失败用例。

## 改动检测与固定合并门禁

新增 `scripts/ci/plan.mjs`，在 job 输出和运行摘要中记录带来源 SHA、基准 SHA、分类原因、必需检查、路径数量与差异摘要的 JSON；不上传具体路径清单。

1. PR 使用目标分支与提交的 merge-base 计算完整差异，测试 GitHub 提供的合并结果；同时记录 head/base/merge 身份。重命名同时检查旧、新路径，删除文件也必须计入。
2. main 使用“最近一个成功范围门禁的祖先提交 → 当前提交”的累计差异。若 A 改代码、B 只改文档且取消了 A，B 仍需执行 A 的代码检查。缺少成功基准、基准不是祖先、历史不可取或 diff 解析失败时执行全量。
3. 使用本地 Git 的完整文件差异，避免依赖平台路径过滤的文件数量限制。PR 分类器使用受信任基线中的规则；本次分类器/工作流变更自身必须触发全量，并单独测试候选规则。
4. 每次 PR/main 事件都启动轻量入口，昂贵 job 用 `if` 条件控制。固定 required check 名称为 `ci-gate`，避免顶层 `paths-ignore` 跳过整个必需工作流后检查一直 pending。
5. `ci-gate` 使用 `always()` 汇总：分类失败、必需 job 失败/取消/意外 skipped、矩阵目标缺失都失败。只有计划明确不要求的 job 才允许 skipped；不能只看“没有 failure”就放行。
6. 手动 `full` 只能增加验证，不能降低规则自动判定的级别。不使用提交消息、PR 标题或任意标签作为跳过测试和安全的开关。

建议保留 main 为唯一长期分支，日常开发使用短期分支与 PR，合并后自动删分支，不增加 develop/release 常驻分支。main 设置 `ci-gate` 必需、禁止强推和删除；工作流与分类规则变更需要评审。若继续直接推 main，同样执行范围检查，但它只能在推送后反馈失败，不能提供合并前拦截。

## 并发、缓存与消除重复工作

- PR 以 workflow + PR 编号分组，main 以 workflow + ref 分组，设置 `cancel-in-progress: true`，让新版本取代过时 CI。取消后的累计差异按上一节处理。
- 正式发布使用独立版本分组，不取消正在执行的签名、公证、上传或发布事务；保留草稿恢复与不可变资产校验。不要假设 concurrency 天然提供严格 FIFO 排队。
- 缓存 pnpm store、Go module/build cache、Cargo registry/build cache、Python 开发工具。key 包含 OS/架构、固定工具链、对应锁摘要及相关编译模式；可用依赖缓存减少下载，不把缓存命中当成测试成功。
- 生产凭据、用户数据库、已安装资料目录不进缓存。真实模型验收可以使用重新校验固定摘要后的下载缓存，安装/就绪验证仍执行。
- 每个流水线内同一份共享 Python/Node 输入只检查一次。Native 和临时旧端供应链可共享扫描结果，但保留各自的完整依赖覆盖、SBOM 身份和结果归属。
- 初期不跨 SHA 复用测试成功结论。发布前任何后续优化都必须校验源码、工作流、工具链、输入摘要和结果来源；安全扫描另受时效及例外到期约束。
- 普通 CI 默认不上传三平台大包；报告与失败日志短期保留，候选包按需保留，正式发行资产长期保留并核对摘要。

## 正式发布流程

Liberty 是桌面应用，CD 的交付结果是可验证的安装资产和 GitHub Release。合并到 main 不自动产生公开发行。

```mermaid
flowchart LR
    A[选择 main 的确切提交与版本] --> B[完整自动化门禁]
    B --> C[三平台构建安装包]
    C --> D[签名与公证]
    D --> E[核验最终资产与安装事务]
    E --> F[绑定草稿 Release ID]
    F --> G[核对资产集合与 SHA-256 后发布]
```

发布候选构建一次，后续验证和上传使用同一批受信任产物，不从 PR artifact 或“最近成功”目录任意取包。签名和公证可能改变文件字节，最终 manifest 与 SHA-256 必须在这些操作完成后重新生成，再对最终安装包验收。

完整门禁必须绑定发行提交；标签解析到的提交和版本来源必须一致。依赖扫描在发布前重新执行并校验现有例外有效期，不因为依赖锁没变而跳过新公告。许可证、SBOM、版本、架构、签名/公证、安装升级回退以及当前正式发布要求均保留。

默认 CI 只有 `contents: read`，使用固定 Action SHA、固定工具链和锁文件。签名凭据仅放在受限制的发布环境；Release 写权限仅给必要的预留/上传/发布 job。若仓库套餐支持，使用 GitHub Environment 限制发布来源和批准；不通过 `pull_request_target` 执行未受信任 PR 代码并授予发布秘密。

自动化全量通过不能替代人工 UI/IME/读屏、注册设备的性能/识别质量、真实外部服务和证书安装验收。发布门禁继续核对这些证据的适用提交或输入范围。当前 Native 仍为隔离候选，流水线重组不自动触发生产切换。

## 实施顺序与验收

1. **建立分类器及其测试。** 覆盖纯文档、混合改动、重命名/删除、共享输入、依赖/工具链、未知路径、diff 失败，以及 main 前一次运行取消的累计改动。
2. **拆分检查入口并接入轻量 CI。** 将现有检查保持为单独可复用单元，去掉每次提交的默认打包和重复安装/测试，加入固定 `ci-gate`。
3. **接入按需全量入口。** 高风险变更、手动验收和正式发布调用同一套完整验证；手动入口可单独选择安全扫描。工作流策略拒绝加入 `schedule` 触发器。
4. **调整候选和正式发布链。** 按确切 SHA/版本绑定，验证所有必要前置结果，保留只读候选与受限发布权限。
5. **校验真实执行并设置分支规则。** 先取得新 `ci-gate` 的真实成功结果，再将其设为必需，移除旧 required check，避免迁移时阻塞所有 PR。

必须验证以下可观察行为：

- 只改 README：仅文档/计划/汇总执行，不安装 Rust/Python，不跑三平台，也不生成候选包。
- 普通 Native 界面改动：只跑对应 Go/生成/UI 检查；不触发旧端全量或完整兼容回放。
- 迁移或凭据改动：自动执行完整相关兼容与 race，必须覆盖对应平台。
- 工作流、分类器或安全例外改动：无法被归为文档，必需门禁被删除/跳过会失败。
- 连续推送代码改动再推文档改动：旧运行被取消，最新运行仍包含未验证的代码检查。
- 某个必需矩阵目标缺失、失败或取消：`ci-gate` 失败。
- CI/CD 工作流不包含 `schedule` 触发器；没有提交、PR、手动或发布事件时，不创建检查任务。
- 普通 main push 不创建 Release；发布入口不能用过期扫描、错误提交或未验证资产发布。

收集实施前后的 runner 分钟数、缓存命中率、文档/普通代码/全量任务耗时、取消率，以及手动或发布前完整验证发现的遗漏。文档检查约 2 分钟、普通变更约 10 分钟可以作为初始优化目标，均不是已测结果或交付承诺；以实际 runner 数据调整。

## 实施与验证记录

2026-11-23 已实现分类器、封闭检查执行器、始终汇总的 `ci-gate`、共同完整门禁和手动候选入口；受控工作流从 `scripts/ci/workflows.mjs` 生成，策略自测拒绝定时触发、权限扩大、缺失必需检查和取消/跳过结果误放行。完整门禁包含 15 个检查单元，版本一致性包含在 policy 内；文档 CHANGELOG 变动也可单独调用 version。

共同完整门禁在旧端退役前包含临时生产端检查，候选打包必须等待全部检查成功。原生本地 `native:verify` 继续独立；未对安装器、签名、GUI、真实模型和生产切换作出新增验收结论。

## 1. 背景与当前差距

当前打工业务并非只有动效：矿场、工厂和便利店已有 SQLite 持久化的岗位状态、真实时间推进、照看阶段、领奖以及宠物物品和 LP 流水。Go repository 测试覆盖任务生命周期与 ledger 原子性/重放；旧 Rust repository 也覆盖状态推进及奖励幂等。

拆分工作线时，原生 `WorkGameView` 的主要操作是点岗位，根据 `idle / needsCare / claimable` 分别开始、照看或领奖；地图、热区与九帧工人动画承担主要视觉反馈。岗位配置已有 `CareActions` 文案，但没有用它们组成操作挑战，相关测试主要核验地图资源、帧、热区位置和缩放。更准确的差距是“有计时经营循环，但缺少可持续的主动玩法”。本轮已追加独立工厂装配练习及交互测试，且把成功完成的装配练习接为可选 care 路径；原有一键照看和岗位经营循环继续保留，其他地图的主动玩法仍未实现。

因此将小游戏体验升级作为 P5 中独立的 P5-G 工作线，单独验证玩法、引擎和输入体验；宠物经济、农场与打工业务迁移另列为 P5-A。P5-G 不阻塞会议处理主链路，也不替代 P5-A 的业务兼容验收。

## 2. 目标与边界

目标是让至少一个已有岗位具备完整、可重复的主动操作循环，并与现有真实时间任务自然衔接。游戏状态、帧更新和画面反馈可以是短期会话状态；岗位状态和奖励仍由应用层与 SQLite repository 管理。

首个原型不改变岗位时长、照看次数、物品产出、LP 区间、加成概率、钱包或 ledger schema。分数、连击或品质只用于本局反馈，不影响经济结算。游戏状态不调用 repository、不写数据库，也不直接发放奖励；可选照看仅在成功终态委托既有 WorkController/application 用例。若后续希望技能成绩影响奖励，需另行修改产品规则、权威业务文档和差分测试，不能从动画或 UI 回调派生结算。

本轮也不要求用游戏引擎重写桌宠或盲盒 3D。桌宠窗口和盲盒视觉有独立的平台、性能与保真验收；它们仍按主重构设计中对应的迁移工作执行。

## 3. 首个可玩切片（P5-G0 已实现）

已从工厂的“基础装配”切入，在“牛马市场 → 工厂打螺丝”增加独立的“练习基础装配”入口，复用原地图、工人素材和原生主窗口。短局不需要开始真实岗位任务；原有开始、一键照看、领奖入口保持原业务规则。岗位需照看时另有可选小游戏入口，只有成功完成当前局才发起一次 care 操作。

已实现的局内循环如下，时长和难度仍需试玩校准：

1. 稳妥单为 6 个配件、60 秒，急单为 10 个配件、45 秒。确定性种子生成包含三种配件且不连续三次重复的订单。
2. 鼠标或 `1 / 2 / 3` 依序装配；原生配件按钮保留 Tab、空格和回车操作，忽略系统按键重复。正确输入立即显示配件、步骤和文字反馈；错序分别扣 3 秒或 5 秒，不倒退已完成步骤。
3. 订单完成或时间耗尽后显示完成数量和准确率，完成态另显示剩余时间，可重开新订单。分数不进入持久化业务。
4. Esc、暂停按钮及主窗口失焦/隐藏/最小化暂停短局，继续操作后才恢复计时；离开入口丢弃局内状态。暂停时卸载活动循环，恢复时重建循环时钟，避免补算后台时间。

原型使用现有工厂地图、工人素材及画布配件/传送带，提供双语、深浅主题和减少动态效果支持。没有新增美术或声音依赖。规则由纯 Go `AssemblyRound` 管理，界面通过固定步长传入活动时间；没有 repository、钱包或奖励服务引用。

如试玩确认该循环有趣且适合原规则，可将一次 care 交互作为入口：玩家主动完成一个短局，结束后仍按原 care 用例更新任务，最终按原 claim ledger 发放既有固定奖励。短局超时只结束短局，不使真实时间岗位任务失败；不能扣除已产生基础奖励，亦不能让用户因未参与短局而无法领取任务收益。是否将 care 改成强制小游戏，须在原型后确认，建议保留一键轻互动/可访问替代路径。

## 4. 渲染与引擎验证顺序

首选先在固定版本的 MyGo 中验证，不先引入外部游戏运行时。当前 MyGo 依赖已包含可选 `plugins/game`：固定步长的游戏更新/输入和 `game.Camera`，可在现有原生窗口内通过 MyGo UI 呈现；主界面仍控制导航、双语、主题、无障碍标签与窗口生命周期。将来可在真实原型中判断其输入、精灵帧、碰撞和绘制能力是否满足体验目标。

只有当 MyGo 原型无法满足明确的游戏需求（例如高频精灵/粒子负载、碰撞或动画工作流、资源导入工具）且这些不足经性能或产品验收证实时，再评估 Ebitengine。Ebitengine 的独立窗口和事件循环需先解决与 MyGo 的窗口、焦点、输入、关闭生命周期及 Metal/D3D11 图形上下文整合；在完成这些验证前，不能假定可以直接嵌入当前窗口。Godot 适用于确需独立场景/美术工具链时的候选方案，但边车会增加进程通信、运行时/包体、安装、签名和故障治理，不作为首个轻量切片默认方案。

目前已用仓库固定的 MyGo `plugins/game` 实现装配切片，并在 Liberty 的 macOS ARM 原生窗口观察到完整订单操作和结果；四目标主程序及测试包编译通过。所需动画负载、输入延迟、会议处理期间资源占用及另外三种目标设备的窗口运行尚未证明，不能据此宣称引擎选型适用于所有后续玩法。引擎依赖不得修改或手工绕过 Go checksum、许可证、OSV/SBOM 和固定版本质量门禁。

局内规则使用调用方传入的时间增量与确定性输入。自动验证覆盖订单、错序扣时、超时、暂停/继续、失焦/隐藏、离开重入、宽窄布局及减少动态效果，另覆盖数字键与原生按钮 Enter/Space 的重复事件。定向回归经过原 WorkController、应用用例和 SQLite，确认只有成功局推进一次 care。旧 Rust 与 Go 的持久化业务对照归 P5-A，实际窗口输入、无障碍和资源测量归 P5-G。后续结果见[实施记录](../plans/2026-11-17-native-desktop-implementation.md)。

### 2026-11-19 验收快照

- macOS ARM 隔离合成资料预览实际确认：中文深色准备画面、开始、一次错配扣 3 秒、数字键完成装配、Esc 暂停/继续、6/6 完成且准确率 86%、重开后归零并更换订单。
- 纯 Go 和组件测试另覆盖两种模式、成功/超时终态、长时间暂停不推进、恢复不追算、鼠标输入、Tab、按键重复、双语及布局。最终 Enter/Space 重复保护经先失败后通过的回归测试确认，未在最终二进制重跑长按实机链路。
- `pnpm check`、`pnpm native:check`、`pnpm native:build:matrix`、`go test -race ./internal/domain ./internal/desktop` 以及预览启动前执行的 Rust/Go 合成兼容检查通过；不代表生产切换、安全发布或其他平台窗口运行通过。

### 2026-11-21 状态反馈与无障碍树回归

- 装配练习的状态栏现在按当前阶段提供双语反馈：进行中播报当前步骤，正确输入播报进度和下一步，错配播报扣时，暂停、完成和超时分别播报当前摘要；恢复练习会清除上一轮命中提示。
- MyGo 组件回归按 `RoleStatus` 核对上述状态，并确认完成/超时不会残留上一条错配状态；覆盖中文和英文。该检查证明组件无障碍树的状态投影，不替代 VoiceOver、Narrator、物理键盘、输入延迟或跨平台窗口验收。
- 玩法局长、策略差异、输入到画面反馈延迟、闲置/会议并行资源预算和 Intel/Windows 实机仍属于未完成的 P5-G1/P5-G3 门槛。

## 6. 主要风险和未定项

- 可玩循环可能打扰宠物照料的轻量休闲定位；需用短局、可跳过和试验后决定是否嵌入正式 care。
- 技能评分如果绑定奖励会改变经济平衡、无障碍要求及旧库兼容口径；当前方案明确暂不这样做。
- 游戏更新频率可能影响闲置 CPU、电池和会议转写期间资源；需要同设备记录闲置和活跃成本，尊重窗口失焦和系统减少动态效果。
- 现有九帧 worker 素材是场景点缀，不代表已有完整可复用动作集；原型不应据此承诺高保真动作玩法。
- Windows x86 虽有构建目标，图形后端及窗口实机尚未验证；必须纳入 P5-G3 或明确保留原客户端路径。

首个练习的时长和键位已按第 3 节落地，care 的可选 UI 路径已接线，但不代表最终玩法定案或完整业务差分完成。其他地图玩法和外部引擎均未实施；原有地图和一键状态操作继续作为兼容入口，经济和业务规则不变。
